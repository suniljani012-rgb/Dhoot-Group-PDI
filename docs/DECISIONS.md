## ADR-001: Technology Stack Selection

**Date:** 2026-08-25
**Status:** Accepted
**Decider:** Principal Architect

### Context
Greenfield project. Need to select frontend, backend, database, storage, hosting, and CI/CD technologies.

### Decision
Adopt the stack specified in the Master Engineering Prompt:
- Web: React + TypeScript + Vite
- Mobile: React Native + Expo + Expo Router
- API: Cloudflare Workers + TypeScript
- Database: Supabase PostgreSQL
- Auth: Supabase Auth
- Storage: Cloudflare R2
- Hosting: Cloudflare Pages
- CI/CD: GitHub Actions
- Package manager: pnpm
- Build orchestration: Turborepo

### Rationale
- Cloudflare Workers: edge-native, globally distributed, low cold-start, cost-effective at scale
- Supabase: managed PostgreSQL with built-in auth, RLS, and migration tooling
- R2: cost-efficient object storage without egress fees, same Cloudflare network
- React Native + Expo: cross-platform mobile with rich ecosystem for camera, biometrics, secure storage
- Monorepo: shared types, validation, and domain logic reduces duplication

### Consequences
- Cloudflare ecosystem lock-in (accepted: benefits outweigh risk at current scale)
- Supabase managed service dependency (mitigated by using standard PostgreSQL; self-hosting possible)
- EAS build required for native iOS/Android (accepted: standard Expo workflow)

## ADR-002: Monorepo with Turborepo + pnpm

**Date:** 2026-08-25
**Status:** Accepted

### Context
Multiple apps (web, mobile, pwa), shared packages, and a backend Worker need coordinated builds and dependency management.

### Decision
Use pnpm workspaces + Turborepo for monorepo orchestration.

### Rationale
- pnpm: efficient disk usage, strict dependency isolation, workspace support
- Turborepo: incremental builds, task caching, parallel execution

## ADR-003: Database-Layer Authorization (RLS)

**Date:** 2026-08-25
**Status:** Accepted

### Context
API-layer authorization alone creates risk of bypassed authorization if API logic is flawed.

### Decision
Enforce authorization at BOTH the API layer (Worker role check) and the database layer (Supabase RLS). Neither alone is sufficient.

### Rationale
Defense in depth. RLS provides a safety net against API logic bugs.

### Consequences
- RLS policies must be maintained alongside API authorization logic
- RLS policy tests required in CI

## ADR-004: Offline-First Mobile Inspection

**Date:** 2026-08-25
**Status:** Accepted

### Context
PDI engineers work in stockyards with potentially weak network connectivity. Inspection failure due to network loss is unacceptable.

### Decision
Mobile app uses SQLite (Expo SQLite + Drizzle ORM) for local persistence with a sync queue for server synchronization.

### Rationale
Engineers must be able to complete inspections regardless of connectivity.

### Consequences
- Conflict resolution logic required
- Idempotency required for all sync mutations
- Increased mobile app complexity

## ADR-005: Cloudflare R2 for Media Storage

**Date:** 2026-08-25
**Status:** Accepted

### Context
PDI inspections generate substantial photo evidence. Storing in PostgreSQL is inappropriate.

### Decision
All media objects stored in Cloudflare R2. PostgreSQL stores only metadata and object references. Access via short-lived presigned URLs generated by Worker.

### Rationale
- R2: no egress fees, S3-compatible, integrated with Cloudflare network
- Presigned URLs: client uploads directly to R2 without routing through Worker body (bandwidth efficiency)
- Metadata in PostgreSQL: queryable, relational, RLS-protectable

## ADR-006: Asynchronous Certificate Generation

**Date:** 2026-08-25
**Status:** Accepted

### Context
PDI certificate PDF generation may be time-consuming for large inspections with many photos and findings.

### Decision
Certificate generation is an asynchronous background job. API returns a job ID immediately; status polling or webhook notifies when complete.

### Rationale
Avoids blocking request threads. Cloudflare Workers have execution time limits that could be exceeded for large reports.

## ADR-007: Dark Mode Deferred

**Date:** 2026-08-25
**Status:** Accepted — Deferred

### Context
Dark mode is desirable but not a v1.0 requirement.

### Decision
Design system tokens are structured to support dark theme addition. Dark mode implementation deferred to post-v1.0.

### Rationale
Design token architecture makes future dark mode addition straightforward. Prioritizing v1.0 functionality first.

## ADR-008: No Custom JWT Cryptography

**Date:** 2026-08-25
**Status:** Accepted

### Context
JWT verification requires cryptographic implementation.

### Decision
JWT verification uses Supabase JWKS endpoint exclusively. No custom cryptographic code written by the project team.

### Rationale
Custom crypto implementations are high-risk. Supabase provides battle-tested JWT infrastructure.
